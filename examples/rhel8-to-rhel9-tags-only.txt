   (sourceware.org/git/glibc.git) if it matters.
glibc 2.28 on the old side, 2.34 on the new: the version a PostgreSQL that
runs it records for a libc collation, where it records one. PostgreSQL 13 or
later warns about a collation, and 15 or later about a database's default
collation, where the version it recorded is not 2.34 (2.28 if it was recorded
on the old side), whether that locale's order changed or not. Where it
recorded 2.34, it does not warn, whatever changed: initdb and a restore on the
new side record 2.34 for every collation, and pg_upgrade there for those of
pg_catalog, for every collation from PostgreSQL 12 or older, and for a
database's default from 14 or older.
!! Not checked for glibc-2.28 and glibc-2.34: they are upstream tags, which
   hold none of a distro's own locale files or patches. Step 2 reads only what
   the tags hold. If the machines run RHEL 8, 9 or 10, name each side as its
   build instead, as rpm -q glibc prints it on the machine without the
   architecture (glibc-2.34-283.el9_8), or as latest-el8, latest-el9 or
   latest-el10.
!! Not compared on any route: the code that compiles and compares the rules
   (localedef's and strcoll's, each build's patches to it included). Only step
   11 sees what it does, when it measures both machines;
   docs/confirming-on-a-real-system.md says how to confirm the order on them.
   No route looks either for a function of a user or of an extension that
   calls glibc's locale functions itself.

      /tmp/pg-glibc-collation-audit/step2_rules_characters.glibc-2.28..glibc-2.34.tsv

      sort, so every rule can change
  sv_FI, sv_FI@euro, sv_SE, swedish
      characters in the changed rules (2): W (U+0057)  w (U+0077)

!! Not compared, no file at glibc-2.28 (2). A file added at the new side
   cannot change what PostgreSQL already stored ONLY IF the locale did not
   exist on the old system, and an upstream tag cannot establish that --
   distros backport. Confirm with `locale -a` on the OLD machine, under the
   names on each line, before treating these as out of scope:
     ckb_IQ -> ckb_IQ
     mnw_MM -> mnw_MM

!! glibc-2.28 and glibc-2.34 hold no localedata/locales/C, the file C.UTF-8 is
   built from, and a distro's build can ship its own, so C.UTF-8's sort rules
   were not compared. PostgreSQL records no collation version for a libc
   collation or database whose locale is C, C.<anything> or POSIX, so no
   version mismatch warns about C.UTF-8; sql/c_utf8_probe.sql, run on both
   machines, compares its order inside PostgreSQL.

Character sets (localedata/charmaps/): 1 of the 30 that the 486 locale builds
in SUPPORTED at both tags use differs between glibc-2.28 and glibc-2.34.
UTF-8: 6485 characters added.
No build's LC_COLLATE names one of those characters.
Transliteration (LC_CTYPE): 24 collating elements of 3 locale builds depend on
a transliteration; none is built differently at glibc-2.34.

Listed in the summary (5): or_IN, sv_FI, sv_FI@euro, sv_SE, swedish
