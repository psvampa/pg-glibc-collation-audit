C.UTF-8 probe output: RHEL8 -> RHEL9

Produced by running ../sql/c_utf8_probe.sql, unedited, on both nodes and
diffing the two outputs. This is the locale the source audit is blind to:
localedata/locales/C exists upstream only from glibc 2.35, so for this pair it
is in NEITHER tag -- see ../docs/limitations.md.

Measured 2026-09-06 on:
  RHEL8 side: Rocky Linux 8.9,  glibc-2.28-251.el8_10.40, PostgreSQL 18.6
  RHEL9 side: Rocky Linux 9.3,  glibc-2.34-275.el9_8,     PostgreSQL 18.6

VERDICT: CHANGED. C.UTF-8 is not code point order on RHEL8 and is on RHEL9.
40 of the 41 probed code points sit in a different position.

Both databases were created with datcollate = C.UTF-8 under the libc provider
and a NULL datcollversion, which is the configuration the limitation is about:
every text column without an explicit COLLATE depends on this order, and no
version mismatch can ever warn about it.

--- the tie detector (query 6b) -------------------------------------------
PostgreSQL breaks a strcoll tie with strcmp, so tied weights are
indistinguishable through SQL from correct byte order. These are strxfrm sort
keys, which cannot hide a tie. RHEL9's keys ARE the UTF-8 bytes, because
codepoint_collation makes strxfrm the identity; RHEL8's are computed weights
and bear no relation to the code point.

RHEL8:
  U+10000 key: ef85b5
  U+20000 key: f0948b95
  distinct weights
RHEL9:
  U+10000 key: f0908080
  U+20000 key: f0a08080
  distinct weights

produces. RHEL8 produces this instead. Note where ASCII lands: at position 31,
after every plane-14-to-16 noncharacter. And note the planes the backported
file declares no range for at all -- 3 through 13 -- whose endpoints sort ahead
