C.UTF-8 probe output: RHEL8 -> RHEL9

Produced by running ../sql/c_utf8_probe.sql, unedited, on both nodes and
diffing the two outputs. This is the locale the source audit is blind to:
localedata/locales/C exists upstream only from glibc 2.35, so for this pair it
is in NEITHER tag -- see ../docs/limitations.md.

Measured 2026-09-06 on:
  RHEL8 side: Rocky Linux 8.9,  glibc-2.28-251.el8_10.40, PostgreSQL 18.6
  RHEL9 side: Rocky Linux 9.3,  glibc-2.34-275.el9_8,     PostgreSQL 18.6

VERDICT: CHANGED. C.UTF-8 is not code point order on RHEL8 and is on RHEL9.
40 of the 41 probed code points sit in a different position.

Both databases were created with datcollate = C.UTF-8 under the libc provider
and a NULL datcollversion, which is the configuration the limitation is about:
every text column without an explicit COLLATE depends on this order, and no
version mismatch can ever warn about it.

The corpus is derived from the RHEL8 file itself, which declares SIX ellipsis
ranges -- planes 0, 1, 2, 14, 15, 16 -- and no range at all for planes 3
through 13. The labels below say which is which, because that distinction is
the finding: the values in undeclared planes fall to UNDEFINED.

$ psql -X -f c_utf8_probe.sql        # on each node, then diff

--- the named pairs (query 3) ---------------------------------------------
U+007F < U+FFFF is the inversion docs/limitations.md records. U+10000 <
U+20000 covers the intra-RHEL8 change, where those code points had no weights
at all before glibc-2.28-93.el8.

--- the tie detector (query 6b) -------------------------------------------
PostgreSQL breaks a strcoll tie with strcmp, so tied weights are
indistinguishable through SQL from correct byte order. These are strxfrm sort
keys, which cannot hide a tie. RHEL9's keys ARE the UTF-8 bytes, because
codepoint_collation makes strxfrm the identity; RHEL8's are computed weights
and bear no relation to the code point.

RHEL8:
  U+10000 key: ef85b5
  U+20000 key: f0948b95
  distinct weights
RHEL9:
  U+10000 key: f0908080
  U+20000 key: f0a08080
  distinct weights

--- the whole order, RHEL8 (query 1) --------------------------------------
Code point order would be U+0001, U+0041, U+005A, U+0061, U+007F, U+0080,
U+07FF, U+0800, U+FFFF, U+10000, ... U+10FFFF -- which is exactly what RHEL9
produces. RHEL8 produces this instead, and the labels make the mechanism
readable:

  * positions 2-4 and 28-30 are the LAST code point of a declared range, all
    six of them -- Bug 22668 is "Fix last character ellipsis handling";
  * positions 5-26 are every code point of a plane the file declares no range
    for, all 22 of them: they have no weight at all;
  * ASCII lands at position 31, behind all of that;
  * positions 38-41 are the FIRST code point of a declared range -- four of
    the five that are in the corpus. The fifth, U+E0000, sorts at 27 instead,
    among the weightless ones. This output records that; it does not explain
    it, and neither does this project.
