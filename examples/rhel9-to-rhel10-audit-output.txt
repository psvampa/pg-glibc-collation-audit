--- What ber_DZ / kab_DZ actually changed: not a rule, a role swap ---

At glibc 2.34, ber_DZ held the full explicit Amazigh/Berber collation rules
and kab_DZ did `copy "ber_DZ"`. At glibc 2.39, kab_DZ holds the same rules
verbatim and ber_DZ does `copy "kab_DZ"`. Both files are correctly flagged
as changed (their content differs byte-for-byte), but the ruleset itself is
identical, just relocated to the other file.

--- What step 5 adds for this pair ---

Tier 1 has real changes, but none that move weights: %Z-to-%z printf format
fixes, {u}int_fast -> {u}int32_t replacements, a misspelling sweep, an -Os
maybe-uninitialized fix, and one new feature -- `codepoint_collation`
(commit f5117c6504), an opt-in LC_COLLATE keyword that no pre-existing
locale uses. Tier 2's linereader.c rework (ADDC/ADDS turned into functions,
UTF-8 input encoding) is a refactor of the tokeniser, not of the weights.

Tier 3 -- the files the include walk reaches that nobody put in a list --
adds two hunks that bear directly on the ko_KR verdict, and both were
invisible before the walk existed:

  locale/programs/linereader.h, in lr_getc, the tokeniser's character reader:
      -  return lr->buf[lr->idx] == '\32' ? EOF : lr->buf[lr->idx++];
      +  return lr->buf[lr->idx++] & 0xff;
  Commit 19d4944459, "locale: Fix signed char bug in lr_getc". It drops a
  '\32' sentinel that truncated input and fixes the sign of the returned
  byte. It changes WHICH BYTES are read out of a locale source file, not how
  a range is expanded, and no glibc locale file contains a \32.

  locale/elem-hash.h, in elem_hash, the collating-element hash:
      -elem_hash (const char *str, int_fast32_t n)
      +elem_hash (const char *str, int32_t n)
  Commit 535e935a28, a tree-wide {u}int_fast -> {u}int32_t sweep. `n` is a
  symbol-name length; the hash value it computes is unchanged.

Neither moves a weight. Nothing changed ellipsis expansion. That is what
lets this pair CLEAR ko_KR rather than only flag it: step 4 still lists
ko_KR (its LC_COLLATE still uses `..`), but with the expansion logic
unchanged, its unchanged LC_COLLATE is now sufficient proof.

The verdict is the same as before Tier 3 existed. What changed is its
standing: it used to rest on not having looked at these two files, and now
rests on having read them. Note that ko_KR's FILE does change in this pair --
lines 6109+, in LC_MONETARY and LC_TIME -- which is exactly why step 2
compares against the LC_COLLATE block rather than the whole file. Steps 1-4 alone could never reach that
conclusion. ardentperf's checksums agree: all ten of their locales,
ko included, are identical between RHEL9 and RHEL10.
