  RHEL9  side: Rocky Linux 9.3,  glibc-2.34-275.el9_8,    PostgreSQL 18.6

VERDICT: UNCHANGED, and structurally so. Both nodes' localedata/locales/C is
byte-identical and declares codepoint_collation, which glibc documents as
discarding all collation information in favour of strcmp/wcscmp. C.UTF-8 is
byte order by construction on both sides, so there is no expansion logic left
for a localedef change to move.

Note on the labels below: they name the ranges the RHEL8-era backported file
declares, because that is the file the corpus is derived from. Neither of these
two nodes declares any range at all -- on them the labels are just names.

--- the tie detector (query 6b), both nodes -------------------------------
The sort keys ARE the UTF-8 encodings of the code points, which is what
codepoint_collation means: strxfrm is the identity. So the "true" above is
real byte order and not tied weights rescued by PostgreSQL's strcmp
tie-break -- the third reading query 2 warns about.

  U+10000 key: f0908080
  U+20000 key: f0a08080
  distinct weights
